# Weekly database backups

Two already-authorized schedules exist and must not compete for the same OCI Object Storage key.

- **Sunday 04:30 UTC (systemd timer, backend):** `shopvivaliz-db-backup.timer` executes the existing `/usr/local/sbin/shopvivaliz-db-backup` wrapper for the Mei email database. The wrapper invokes the installed verified database backup script for the precise `mei-email` target. It runs one writer to OCI and verifies remote backup metadata/checksum; this schedule and service are not modified by the repository workflow.
- **Sunday 06:15 UTC (GitHub Actions):** `weekly-database-backups.yml` on `mei-backend` uses the versioned `scripts/ops/shopvivaliz-db-backup.py` to back up two independent **local** Solange Docker targets, then executes `scripts/verify-mei-systemd-backup.py` in read-only mode to check the existing Mei backup. The `mei-ci` secondary-host job still runs the same `--profile secondary` backup for MLRR.
- The GitHub workflow retains `workflow_dispatch`, self-hosted runner labels, concurrency and fail-closed checks. The later steps use `if: ${{ !cancelled() }}` so a failure of the first local Docker target does not suppress later verification, but the **overall job remains FAILURE** if any step fails. Do not add `continue-on-error`, retries, new writers or bypasses.

## Exactly what is and is not verified

- `solange-production` is a **local Docker database**, not the Solange app's managed Supabase production source unless independently established.
- `solange-staging` refers to the **legacy local demo Docker database** `supabase_db_solange-client-demo`, **not** the published app's Supabase managed staging database. It has no host-published PostgreSQL port, and both schema-only and full read-only pg_dump canaries exited 139 on 08 Nov 2026. It must remain failed until the real cause and restore are verified; do not publish a database port or silently skip it.
  - **2026-11-08 verified repair path:** the Docker image's PostgreSQL 15.8 `pg_dump` crashes with exit 139, but the backend host PostgreSQL **16.15** client connected successfully over the *same container's private Unix socket* `/proc/<container-pid>/root/run/postgresql` (schema-only and full dry runs, stdout discarded, no backup artifact), with no published port, network firewall change, credential transfer or schema mutation. The versioned script now uses `sudo -n /usr/bin/pg_dump` only for this fixed, allowlisted local demo target, after validating Docker container ID, image, user, database, running+healthy state and PID and rechecking identity afterward. The normal temp-archive/pg_restore/OCI checksum verification remains mandatory. The CI runner remains `ubuntu`; only the host client process is elevated. **This is not a certificate of a real OCI backup or isolated restore until the next authorized workflow run passes**.
- `mei-email` is owned by the **systemd single writer**. The GitHub workflow **must not invoke a second backup command for it**. Its read-only verifier requires a successful recent systemd service run, active timer, and fresh OCI dump + `.sha256` metadata in the correct order and within bounded time. It obtains OCI namespace/bucket/CLI from string constants in the existing trusted host backup script without loading credentials or running it. OCI HEAD metadata does not prove the full remote hash or isolated restore. Perform restore verification separately.
