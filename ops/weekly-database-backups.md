# Weekly database backups

Two already-authorized schedules exist and must not compete for the same OCI Object Storage key.

- **Sunday 04:30 UTC (systemd timer, backend):** `shopvivaliz-db-backup.timer` executes the existing `/usr/local/sbin/shopvivaliz-db-backup` wrapper for the Mei email database. The wrapper invokes the installed verified database backup script for the precise `mei-email` target. It runs one writer to OCI and verifies remote backup metadata/checksum; this schedule and service are not modified by the repository workflow.
- **Sunday 04:30 UTC (Marina systemd):** `shopvivaliz-db-backup.timer` on `marina-a1-4c24g` executes the existing root-owned `/usr/local/sbin/shopvivaliz-db-backup` wrapper, whose exact target is `/usr/local/sbin/shopvivaliz-db-backup.py --profile secondary --target mlrr-phase3`. This is the **only MLRR OCI writer**; never launch a second writer from GitHub Actions.
- **Sunday 06:15 UTC (GitHub Actions):** `weekly-database-backups.yml` on backend `mei-backend` runs the two source-controlled local Solange Docker backups independently and checks existing MEI systemd/OCI evidence read-only; its `secondary-host` on Marina `mei-ci` **only** runs `scripts/verify-mlrr-systemd-backup.py`, reads the root-owned installed writer identity + successful recent service/timer and verifies the exact offsite OCI MLRR dump and `.sha256` headers in a bounded time window. Both hosts fail closed without starting additional Mei/MLRR backups.
- The GitHub workflow retains `workflow_dispatch`, self-hosted runner labels, concurrency and fail-closed checks. The later steps use `if: ${{ !cancelled() }}` so a failure of the first local Docker target does not suppress later verification, but the **overall job remains FAILURE** if any step fails. Do not add `continue-on-error`, retries, new writers or bypasses.

## Marina MLRR secondary single-writer correction (Audit V5, issue #198)

The original GitHub `secondary-host` command `/home/ubuntu/.local/bin/shopvivaliz-db-backup.py --profile secondary` is not installed on Marina, and normal runner `ubuntu` does not have direct permission to open its Docker socket. More importantly, Marina already has a verified **root-owned weekly systemd writer**. The workflow therefore must not attempt to re-create this writer or request broader Docker permissions. Its only role is to **attest the existing writer** on the correct host and confirm the recent offsite OCI objects.

Evidence on 08 Nov 2026 UTC: Marina `shopvivaliz-db-backup.service` `Result=success`/`ExecMainStatus=0`, finished **04:33:21 UTC**, timer `active`; OCI Object Storage `db-backups/secondary/mlrr-phase3-latest.dump` last-modified **04:33:16 UTC**, **307,814 bytes**; `.sha256` last-modified **04:33:18 UTC**, **90 bytes**. `mlrr-pg-prod` Postgres 16 container exists and is running (root-authorized Docker inspection); no port, container, credential or service was changed. Do not assume OCI metadata proves a restored database; preserve a separate isolated restore drill.

The secondary verifier rejects mismatched host/operator, untrusted local root-owned wrapper/script, wrong native `--profile secondary --target mlrr-phase3` binding, Docker container/profile drift, stale/failed systemd timer or service, missing/reordered/undersized OCI dump/manifest and unreadable OCI. It does not read DB contents, use Docker, run a dump, write to OCI, copy credentials, relax grants or certify the separate managed Supabase staging application database (`solange-rolla-consultorio#191`).
